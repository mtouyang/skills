# Matt Pocock Skills — repo guide for agents

This repo is a collection of **agent skills**: Markdown `SKILL.md` files (plus supporting reference files) that Claude Code, Codex, and other Agent-Skills-compatible harnesses load as slash commands and behaviours. There is no application code, build step, or test suite. The "product" is the prose in the skills, and the work is keeping that prose, its metadata, and the indexes that point at it consistent with each other.

`AGENTS.md` is a symlink to this file, so edit `CLAUDE.md` only.

## Repository layout

```
skills/<bucket>/<skill-name>/   one folder per skill (see "Anatomy of a skill")
docs/<bucket>/<skill-name>.md   human-facing docs pages, promoted buckets only
README.md                       public landing page and the skill reference index
CONTEXT.md                      domain glossary for this repo (Issue tracker, Issue, Decision ticket, Triage role)
CHANGELOG.md                    generated by Changesets; don't hand-edit
.claude-plugin/plugin.json      Claude Code plugin manifest: version plus the promoted skills list
.claude-plugin/marketplace.json the repo as its own single-plugin marketplace
.changeset/                     pending release notes (one .md per change)
.agents/invocation.md           user-invoked vs model-invoked rules
.agents/writing-docs.md         how to write a docs page (template and "done when" checklist)
.agents/adr/                    architecture decision records for the repo itself
.out-of-scope/                  rejected feature requests and why (read by the `triage` skill)
.github/workflows/release.yml   Changesets "version" PR on push to main
scripts/link-skills.sh          dev-only: symlink every skill into ~/.claude/skills and ~/.agents/skills
scripts/list-skills.sh          prints every SKILL.md path
```

## Buckets

Skills are organized into bucket folders under `skills/`:

- `engineering/` — daily code work
- `productivity/` — daily non-code workflow tools
- `misc/` — kept around but rarely used, not promoted
- `personal/` — tied to my own setup, not promoted
- `in-progress/` — drafts not yet ready to ship
- `deprecated/` — no longer used

`engineering/` and `productivity/` are the **promoted** buckets. Everything else is non-promoted.

## Anatomy of a skill

```
skills/<bucket>/<skill-name>/
  SKILL.md               frontmatter + instructions (required)
  agents/openai.yaml     Codex UI metadata (required, every skill)
  *.md                   optional reference files the SKILL.md links to (e.g. tdd/tests.md)
  scripts/               optional helper scripts
```

- The frontmatter `name` must equal the folder name.
- `agents/openai.yaml` holds `interface.display_name` and `interface.short_description`. For user-invoked skills it also holds `policy.allow_implicit_invocation: false`.
- Supporting reference files are linked from `SKILL.md` with relative links inside the skill's own folder. Don't use `../other-skill/FILE.md` cross-links. Put shared material in the skill that owns it; other skills reach it by invoking that skill in prose ("Run the `/grilling` skill").

### Invocation

Every `SKILL.md` is either user-invoked (`disable-model-invocation: true` plus `policy.allow_implicit_invocation: false` in `agents/openai.yaml`, reachable only by the human) or model-invoked (model- or user-reachable). See [.agents/invocation.md](./.agents/invocation.md). In short:

- **User-invoked**: the `description` is a human-facing one-liner with no trigger lists. These skills orchestrate.
- **Model-invoked**: omit both flags. The `description` is model-facing, with rich trigger phrasing ("Use when the user wants…"). These skills hold reusable discipline.
- Keep the two harness flags in sync. A user-invoked skill may invoke model-invoked skills but never another user-invoked one.

For guidance on writing the skill prose itself, see [`writing-great-skills`](./skills/productivity/writing-great-skills/SKILL.md).

## Indexes that must stay in sync

Every skill in `engineering/` or `productivity/` (the **promoted** buckets) must have a reference in the top-level `README.md` and an entry in `.claude-plugin/plugin.json`'s `skills` array (the Claude Code plugin ships exactly the promoted set). Skills in `misc/`, `personal/`, `in-progress/`, and `deprecated/` must not appear in either.

Each skill entry in the top-level `README.md` must link the skill name to its `SKILL.md`.

Each bucket folder has a `README.md` that lists every skill in the bucket with a one-line description, with the skill name linked to its `SKILL.md`. The promoted buckets' `README.md`s and the top-level `README.md` group entries into **User-invoked** and **Model-invoked**. Non-promoted bucket `README.md`s (`misc/`, `personal/`, `in-progress/`, `deprecated/`) use a flat list.

### Docs pages

Skills in `engineering/` and `productivity/` also have a human-facing docs page at `docs/<bucket>/<skill-name>.md` (the docs tree mirrors those two bucket folders under `skills/`). The published URL is `https://aihero.dev/skills-<skill-name>` regardless of bucket; the docs path is repo organisation only. When you add, rename, or change the behaviour of a skill in `engineering/` or `productivity/`, create or re-sync its docs page following [.agents/writing-docs.md](./.agents/writing-docs.md). Docs pages use **absolute links only** and have no H1. Skills in the non-promoted buckets (`misc/`, `personal/`, `in-progress/`, `deprecated/`) get **no** docs page.

### The `ask-matt` router

[`ask-matt`](./skills/engineering/ask-matt/SKILL.md) is the router that maps every user-reachable skill and how they relate. The same trigger that re-syncs a docs page applies to it: whenever you add, rename, remove, or change how a user-reachable skill fits the flows, re-read `ask-matt`'s `SKILL.md` and update it so the map stays accurate. A router that never mentions a new skill, or still routes to a stale one, gives wrong answers.

## Checklists

### Adding, renaming, or moving a skill

1. Create or move the folder under the right bucket. Set the frontmatter `name` to match the folder, and add or update `agents/openai.yaml`.
2. Pick the invocation mode and set both harness flags (or neither).
3. Update the bucket `README.md`, and the old bucket's too if the skill moved.
4. If the skill is promoted, or is being promoted or demoted:
   - add, remove, or rename it in the top-level `README.md` under the right bucket and invocation group
   - add, remove, or rename its path in `.claude-plugin/plugin.json` `skills`
   - create, move, or delete `docs/<bucket>/<name>.md`
   - update `ask-matt`
5. Grep for the old name across `skills/`, `docs/`, and `README.md` when renaming. Skills refer to each other by `/name` in prose.
6. Add a changeset (see below) for changes users will notice in promoted skills.
7. Re-run `scripts/link-skills.sh` locally so installed skills pick up the change.

Quick consistency check for the promoted set:

```bash
for d in skills/engineering/*/ skills/productivity/*/; do
  d=${d%/}; n=$(basename "$d"); b=$(basename "$(dirname "$d")")
  grep -q "\"./$d\"" .claude-plugin/plugin.json || echo "missing in plugin.json: $d"
  grep -q "$d/SKILL.md" README.md             || echo "missing in README.md: $d"
  [ -f "docs/$b/$n.md" ]                       || echo "missing docs page: $n"
done
```

### Changing a skill's behaviour

Edit `SKILL.md` and any reference files. If the skill is promoted, re-sync its docs page, check `ask-matt` and the README one-liners, and add a changeset.

## Releases and versioning

- Versioning uses [Changesets](https://github.com/changesets/changesets). A single package, `mattpocock-skills`, is versioned. Add a file in `.changeset/` for each user-facing change:

  ```md
  ---
  "mattpocock-skills": minor
  ---

  Plain-language description of the change, naming the skill in **bold**.
  ```

  (`npm run changeset` does the same interactively.) On push to `main`, `.github/workflows/release.yml` opens a "chore: version skills" PR that runs `changeset version`, which bumps `package.json` and writes `CHANGELOG.md`.
- The repo is also its own single-plugin Claude Code marketplace: `.claude-plugin/marketplace.json` lists the one `mattpocock-skills` plugin. When bumping the release version, keep `.claude-plugin/plugin.json`'s `version` in sync with `package.json`'s. Claude uses the plugin `version` to decide when installed users see an update. `changeset version` does **not** touch `plugin.json`, so update it by hand.
- Run `claude plugin validate . --strict` after touching either manifest.
- The reason there is a Claude plugin but not (yet) a Codex one is recorded in [.agents/adr/0002-ship-as-a-claude-code-plugin.md](./.agents/adr/0002-ship-as-a-claude-code-plugin.md). Don't add a `.codex-plugin/` without revisiting that ADR.

## Local development

To (re)link every skill into the local harness skill directories (`~/.claude/skills`, `~/.agents/skills`), run `scripts/link-skills.sh`. Each entry is a symlink into this repo, so a `git pull` keeps installed skills current. Re-run the script after adding, removing, or renaming a skill. It skips `deprecated/`. It is a maintainer-only script, and requests to change it are not accepted.

## Conventions

- **Domain vocabulary**: use the terms in [`CONTEXT.md`](./CONTEXT.md). Say **Issue tracker**, not "backlog"; **Issue**, not "ticket", except for a wayfinder **Decision ticket** or the `to-tickets` artifact.
- **Setup dependency**: only hard-dependency skills (`to-tickets`, `to-spec`, `triage`) carry an explicit "run `/setup-matt-pocock-skills` if not" pointer. Soft-dependency skills refer to the domain glossary and ADRs in vague prose. See [ADR 0001](./.agents/adr/0001-explicit-setup-pointer-only-for-hard-dependencies.md).
- **Passive vs active domain work**: reading `CONTEXT.md` for vocabulary is a one-line prose pointer. Only active glossary and ADR building is the `domain-modeling` skill.
- **Rejected ideas**: before proposing a feature, check `.out-of-scope/` (for example, no hard cap on grilling questions, and only mainstream issue trackers are supported).
- **Leading words**: skills and docs share vocabulary (_seam_, _deep module_, _tracer bullet_, _grill_, _decision tree_). Reuse the existing term rather than coining a synonym, and rename everywhere if a term changes.
- Commit style follows Conventional-ish prefixes (`feat(skill):`, `fix:`, `docs:`, `refactor(skill):`), or a plain imperative summary.
